# Current v6 GPU prover compatibility

2026-10-22. Source-only triage; no installation, build, GPU use, proof generation, active outcomes or private evaluation data. This does not authorize a cryptographic port.

**Decision: no demonstrated drop-in path for the current prover in the two upstream paths reviewed. Defer adoption.** An MSM-only adapter is a plausible later qualification target; a complete prover replacement is substantially less compatible. No speedup, VRAM fit or Forge device compatibility was measured.

## What must remain identical

The project at `9e0dca5851f80a3c9fd9e09db1cc7f340aaf8e02` calls `Groth16::<Bn254>::create_random_proof_with_reduction` with `OsRng`. Cargo pins arkworks **0.6.0**; “v6” separately names the current two-input relation, with authorization magic `KPICU06\0`. Upstream 0.6 defaults to `LibsnarkReduction`; its implementation synthesizes constraints on CPU and calls arkworks G1/G2 MSM directly, with no selectable GPU backend. [Pinned arkworks prover](https://github.com/arkworks-rs/groth16/blob/0bb3e604c534bd118ed477eaf1231f591d6fc40f/src/prover.rs), [default reduction](https://github.com/arkworks-rs/groth16/blob/0bb3e604c534bd118ed477eaf1231f591d6fc40f/src/lib.rs).

Local `two_input/wallet.rs:658–734` checks the existing proving-key length/hash, checked compressed deserialization, trailing bytes and equality of its embedded VK to the pinned VK. `harness.rs:18–21,134–143` serializes the proof using arkworks compressed encoding after CPU verification. `covenant.rs:200–202,617–633` requires a 328-byte VK, a 128-byte proof and native `OpZkPrecompile` tag `0x20`. A compatible accelerator must preserve those bytes/identities and the public-input order, not merely use a curve called BN254.

Native KAS backing, authorization, value conservation, deterministic rejection and independent exits remain invariants. An accelerator must remain optional; it cannot make a GPU operator or licensed service necessary to withdraw. CPU verification catches invalid proofs, but does not establish witness confidentiality, correct blinding randomness or resistance to implementation side channels. See project [SECURITY-INVARIANTS.md](../../../../SECURITY-INVARIANTS.md), especially I-1/I-3/I-5/I-7/I-9/I-10/I-15.

## Smallest decision-changing checks — future, not executed

**A: qualify the arithmetic boundary first.** If a separate port is later authorized, use only public synthetic values: up to eight G1 and eight G2 points, including infinity/cancellation, and scalars covering zero/one/modulus-minus-one. Compare canonical, validated GPU results exactly with pinned arkworks 0.6 CPU MSM. Check Fq2 component order, Montgomery conversion and coordinate conventions explicitly; do not assume Rust memory layouts match. Keep QAP/NTT on CPU. One device/worker suffices; GPU initialization/build costs are unknown and no runtime or VRAM estimate is claimed. Any mismatch, unchecked conversion or forced arkworks downgrade stops this path. Passing only moves the decision from “unsupported integration” to “bounded adapter qualification worth considering.”

Before actual adoption, use one existing **public development v6** fixture with its unchanged PK/VK, circuit and public inputs. For test-only reproducibility, feed identical fixed nonzero r/s to CPU and candidate through explicit-blinding interfaces: require identical canonical A/B/C and 128-byte proof, then verify independently with arkworks CPU **and the pinned Kaspa native path**. Mutating a public input/proof must reject. Ordinary OsRng proofs need not be byte-identical. Preserve production randomness. A toy circuit alone cannot qualify the v6 relation; budget for the full fixture needs a separate decision based on measured resource needs.

**B: the cheap falsifier is already negative.** The current public API cannot consume the pinned key, and its default blinding path differs. Do not build it now. Reconsider only after an independently reviewed, source-level adapter maps the existing key/reduction exactly and preserves cryptographic randomness without a new ceremony or circuit. It would then need the same deterministic CPU/native cross-check above. A new snarkjs setup or successful proof of a different toy circuit would not change this decision.

These are compatibility gates, not privacy pass criteria. They do not change the failed working-balance policy, absolute privacy requirement, frozen experiment or observer-acceleration plan.
