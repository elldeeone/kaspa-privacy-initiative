# Additive stale-worker cancellation check

Selected after the original frozen race measured 437.817 seconds of obsolete
proving and a successful 877.720-second withdrawal using the original approvals.
The original selection, failed-work evidence and two full histories stay intact.

Question: after learning the bank changed, can the coordinator stop its own
obsolete CUDA worker cleanly and generate the valid replacement without any new
wallet approval? This is an application/process fix, not a new consensus rule,
circuit, native program or authorization meaning.

Run only after the original GPU campaign finishes. Reverify its two complete
histories. Start a genuine proof from its now-obsolete public work item, then
simulate learning of the already demonstrated bank advance after 30 real seconds.
Require live owned CUDA work, interrupt only that process group, verify owned
workers stop, and start a genuine fresh proof of the exact already-qualified
current replacement input. Do not use a cached completed replacement proof.

This supplements the original actual-advance-during-proving experiment. It does
not claim to observe another fresh chain advance. Detection delay is a declared
timer; clean cancellation and fresh proving are actual process measurements.

Reverify the fresh SDK receipt and actual native history using the frozen
verifier. Replace only the old native proof witness in a separate replay copy.
The input, journal, transaction body/payload and native IDs must remain identical;
every child/payout spend must still validate. Never alter the original records.
This requires no wallet backup or proving parameter file.

Record cancelled work, cleanup time, replacement proof time and the unchanged
original approval digest. Preserve partial artifacts and source hashes. Stopping
the stale worker does not guarantee success under repeated independent advances.
This is a supplementary worker-control result, not a new measured complete busy
arrival comparison. Any retimed end-to-end savings remain explicitly derived.
