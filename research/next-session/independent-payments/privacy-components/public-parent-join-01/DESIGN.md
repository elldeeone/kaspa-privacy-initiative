# Explicit public parent-field join for the retained recipient spends

Status: separate read-only addendum before execution. Preserve every byte of the original103-path component packet. The original fresh public verifier ran standalone Transaction::Validate and the controller compared input IDs/counts. It did not independently join each input's commitment and authorization key to the corresponding aggregate output. The earlier DESIGN's combined wording was broader than that evidence.

Use only the already-published aggregate, the two recipient spends and their retained observations. Authenticate them against the frozen103-path manifest; use the already-built source-pinned public inspector to deserialize/recompute public hashes and expose fields. No new owner/recipient process, signing, proving, range-proof/signature validation, private key access, random draw, upstream change or blockchain/network operation is involved.

For each actual one-input recipient spend, select exactly one parent output by its computed public output ID. Require input.spent_output_id equals parent.output_id; input.commitment equals parent.commitment; input.output_pubkey equals parent.receiver_pubkey (Ko). Require the joined ID also matches that recipient's retained received-output observation and that the two recipients consume different parent IDs. Compare publicly serialized kernel fees to the retained fee observations. Hidden input/output values cannot be recovered from public commitments: label the observation's amount/fee equation as metadata, not independently checked plaintext wire amounts.

Calibrate the join with pure copies of inspected public fields: preserve ID but substitute the other parent's commitment; preserve ID/commitment but substitute the other parent's Ko; substitute the other parent ID while keeping original fields; substitute all three parent fields while retaining the original recipient receipt; and use an absent parent ID. Each must reject at the expected join boundary. These copies are data-validation controls, not newly signed transactions, signature/range-proof checks or claimed chain-valid attacks.

A passing join plus the retained standalone cryptographic validation supports an explicit local parent-field relationship for these supplied public objects. It does not establish an accepted UTXO, global unspentness, no competing chain spend, currentness, reorg handling, financial privacy or native KAS compatibility. No original observation is rewritten or silently promoted into a chain claim.
