## Outer proof and joint witness are different proposals

**Outer proof over independently produced v6 proofs:** each wallet can keep its note openings, spending/viewing keys and private membership witness locally while producing its existing `Bundle`. A collector could receive the authorization, proof and ciphertext pair as an outer prover's private witness. Those values are already sufficient to verify the inner proof; the collector would not need the wallet's spending secret or output-note openings for that verification. This is a plausible *contribution boundary*, not an implemented batching interface. The collector still knows grouping and submission provenance. Publishing the inner bundles, individual authorization digests or separately testable proofs preserves the toy's failed-exposure variant.

The missing outer relation must do more than verify two proofs: bind a fixed inner VK and pool domain; parse their authorizations and recompute their public-input digests; constrain the permitted modes/fees; bind the complete flattened CM/ciphertext pairs and NFs to the hidden partition without omission or substitution; authenticate the anchors and current spentness/state transition. Current inner proofs leave current spentness to the covenant (`circuit.rs:1`, `tree.rs:218-260`). Merely verifying both proofs does not prove fresh, nonduplicated, authorized batch settlement. No such relation, recursive verifier or aggregator entry point appears in the scoped `poc/shared-pool/src`/`Cargo.toml` sources inspected.

**New joint-witness circuit:** combining the two private value/ownership relations directly requires all private inputs at the prover. Current `Input` contains the note, spending secret, position, Merkle path and dummy material (`circuit.rs:14-22`); `harness::selected` copies the spending key (`harness.rs:33-42`). `Prepared` deliberately holds this material in process and is not serializable (`wallet.rs:617-626`). The current prover consumes that full circuit (`wallet.rs:718-734`). There is no supplied MPC/distributed proving protocol that lets independent owners populate a joint witness while withholding their secrets from a collector. Giving a collector those current inputs changes the trust model and can disclose spend authority. A joint circuit also needs new parameters/VK. It is not an implementation of “aggregate existing proofs.”

Toy validation has all fixture openings and each `Operation.secret` available (`check.py:229-272,356-379`). That is appropriate for a reference checker, but it supplies neither the secret-free outer verifier nor private multi-party joint proving. The recipient API's own-key restriction answers a different question.

## Native acceptance and setup boundary

**Existing pool: neither proposal is compatible.** Its P2SH covenant demands one 128-byte proof, the fixed payload length and fixed operation layout, hashes the public authorization into exactly two inputs, and invokes `OpZkPrecompile` with the embedded v6 VK (`covenant.rs:200-240,597-619,627-634`). The successor reconstructs the same script prefix/suffix around changed state; the suffix contains the VK (`covenant.rs:116-132`). There is no general upgrade or alternate-batch branch. New proof bytes cannot change that accepted relation or switch the reserve to a new covenant. Do not propose an in-place migration.

**A new pool may be able to use existing consensus primitives; it still needs a new setup and contract.** At the pinned native dependency, Groth16 verification reads a supplied BN254 VK, proof and input count, checks VK/input arity and resource limits, then verifies the proof. It does not restrict VKs to KPI's v6 circuit (`crypto/txscript/src/zk_precompiles/groth16/mod.rs:20-61,64-119`). Thus a sound new BN254 outer or joint circuit with a compatible receipt need not inherently require a new consensus opcode. This is an interface observation, not evidence that a candidate fits limits or works. The current v6 covenant's 328-byte VK/two-input rule is pool-specific; replacing that circuit requires a new pinned PK/VK and newly founded pool script. The existing setup routine generates parameters for the actual circuit (`harness.rs:161-184`), and wallet loading checks the exact PK and embedded VK (`wallet.rs:667-705`).

Supported native tags are Groth16 and R0 succinct (`zk_precompiles/tags.rs:7-20`). That list does not select or provide the missing outer implementation. A receipt for an unsupported proof type cannot simply be passed to this verifier; any claim about using a different backend must map its exact final receipt to a supported interface first. No fresh consensus or upstream state was inferred beyond the pinned dependency.

## Only the next smallest genuine gate

**DEFER now.** Before allocating proof/GPU/build resources, name an existing concrete outer-verification implementation and pin its source/dependencies, inner-verifier relation, final native-supported receipt and setup requirements. This is an implementation-selection prerequisite, not another toy experiment. A claim that the current Groth16 prover automatically supplies recursion fails this prerequisite.

If that prerequisite is satisfied, the smallest genuine check is **one offline outer-verifier compatibility fixture over two retained public v6 proof bundles**, using only their public authorizations, proofs, ciphertexts and pinned inner VK. It must hide the inner grouping from the public outer statement, bind a fixed declared aggregate digest, reject a modified proof/auth/ciphertext binding, and have its final receipt accepted by the pinned native proof interface. It must require no wallet key, note opening or private ledger. This tests the missing proof-composition/native-receipt boundary only; it is not a batching privacy result or a complete pool. Do not combine it with a new wallet, full batch covenant, native exit demonstration, deployment or workload benchmark at this stage. Cost is unknown until an implementation is selected; the toy's runtime provides no budget estimate.

If no supported implementation can be named without a new cryptographic subsystem, keep heavy batching deferred. The current evidence supports preserving the toy as a conditional architecture observation, not scheduling the report's proposed end-to-end proof-and-native-exit experiment.
