# Six-guard preparation prototype

Source prototype only; the live campaign still uses its selected preparation code.
No benchmark, RPC, financial admission or live activation is authorized by this note.

`chain/cache_prepare_parallel.mjs` runs at most six independent invocations of
the same unchanged helper09 command used by `public.mjs`. Each read retains the
fresh private-inode exclusions, single-link check and expected whole-file SHA.
There is no persistent server, guard override or new cache authority.

Flattened indices preserve the old primary/post page order. The old `prefixData`
function supplies trimming; canonical encoding, gzip level, fingerprints, graph
metadata and exclusive copy flags retain the original semantics. A failure stops
new scheduling and settles all started helpers before returning. Partial output
is retained, and is never a successful cache admission.

The independent pure controls passed 19 mocked checks, including byte/record
equivalence, out-of-order completion, the six-reader bound and failure cleanup.
They made zero actual prototype helper calls, copies or network requests.

The proposed public-217 benchmark compares preparation with the original
full-trace preparation output. That trace later failed acquisition: its golden
files are **preparation evidence, not accepted financial state**. Both golden
and new copies receive fresh unchanged-helper reads and full-byte comparison
after timing. The historical 716.642-second serial observation is unpaired;
different host load prevents a controlled speedup claim.

Root must select the exact source/corpus manifest before running the benchmark.
Retain all selected baseline and golden paths until it finishes. Existing cache
admission, runtime68 and financial replay remain mandatory and unchanged; any
future use needs explicit new outer source provenance.
