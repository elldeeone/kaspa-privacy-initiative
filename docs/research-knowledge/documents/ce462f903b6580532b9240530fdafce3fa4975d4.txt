## Findings that should be resolved before bounded execution

### R1 — P2: allocation limits are checked after the expensive allocation

`capsule/adapter.py:54–70` first duplicates the candidate reference list, creates a dictionary entry per candidate, builds a Python list containing a seven-element list per candidate, and materializes the full NumPy array. Only then does it check the advertised 1-GiB packed-input cap. A fixture large enough to violate the cap has already incurred the allocation, while the original Python candidates, index dictionary and temporary packed lists also exist. The advertised 8.7M loose record bound is therefore not a process-memory bound.

The parent RSS stop at `benchmark.py:134–137` is explicitly sampled, not a hard limit. It can terminate a process after observing excess, but cannot prevent an allocation burst or host OOM between samples. This is especially relevant before GPU launch: the CPU candidate construction and packing happen first. `BENCHMARK.md:29` correctly acknowledges sampled limits; it does not cure the late input-cap check.

**Prerequisite:** reject the known candidate-count/byte bound before packing; allocate/fill a bounded contiguous array or chunks without a second large Python row representation. Give the whole worker a supported per-job hard memory boundary, or document a conservative fixed-fixture peak budget with an explicit parent acceptance of sampled enforcement. Do not silently increase the 4-GiB stop to obtain a successful result.

### R2 — P2: timeout cleanup can exceed the promised time budget

`benchmark.py:149–162` sends TERM, waits three seconds, sends KILL, waits another three seconds, then always calls `process.wait()` without a timeout. If the KILL/reap path itself does not finish—for example a task stuck in an uninterruptible driver wait—the second timeout reaches the unbounded `finally` wait. The 300-second worker / 1,800-second controller limit no longer bounds completion, and `resource.json` is not written until that wait finishes (`:163–168`). The setup recipe similarly uses `timeout 900s` without a kill-after bound (`BENCHMARK.md:43`).

This is **not** an allegation that ordinary Bubblewrap descendants automatically escape process-group termination. The installed Bubblewrap manual says `--die-with-parent` kills the sandbox chain with SIGKILL when Bubblewrap or its parent dies; the package enables it, plus a PID namespace (`benchmark.py:94–97`). That is a useful safeguard. However, the controller neither bounds its final wait nor records a final descendant/device-owner cleanup audit.

**Prerequisite:** remove the unbounded wait, persist failure/resource state before potentially blocking cleanup, give escalation a finite outer bound, and verify the job's recorded descendants/device ownership are gone before scheduling another worker. If a process cannot be reaped, report a blocked cleanup state and stop orchestration rather than claiming completion. Give setup its own bounded escalation and retained failure log.

### R3 — P2: the advertised total-device VRAM stop is not what is measured

`gpu_processes()` queries only `--query-compute-apps=pid,used_memory` (`benchmark.py:78–91`); `:138–146` sums those per-process values. It does not query device-wide used memory, so graphics allocations and driver/device allocations absent from that list are outside the stated “total” value. This is different from [REPORT.md:63–65](REPORT.md) promising a 3-GiB observed total GPU stop and separate total-device measurement. A new unrelated **compute** process is detected, but other device consumers are not.

The 2-GiB CuPy pool cap is configured twice (`benchmark.py:103`, `capsule/adapter.py:45`) and is useful; it is not a complete device limit. The code and document already correctly acknowledge that RSS/VRAM sampling can miss brief peaks.

**Prerequisite:** either enforce and record the promised device-wide stop and baseline, or explicitly change the budget to per-job compute-process usage with a separately checked device headroom/consumer rule. Keep the distinction in result field names. A missing/non-numeric telemetry result should remain a blocking condition, as it currently does.

### R4 — P2: the frozen input list is not a closed execution capsule

`verify_inputs()` checks each named leaf and hash (`benchmark.py:50–56`), but does not reject symlinked parent directories, absolute/escaping manifest paths, or extra importable files. The worker mounts the entire `capsule` directory and inserts `/code` into `sys.path` (`benchmark.py:98`, `capsule/worker.py:13`). Thus a later unmanifested helper or matching cached bytecode can enter execution without being covered by the named hashes. `-B` prevents writing new bytecode; it does not establish that existing bytecode is absent. No such extra file or symlink exists in the reviewed snapshot, so this is a dispatch-integrity gap, not evidence of contamination.

Similarly, setup/run/cache destinations have no ancestor-link containment checks (`SETUP.sh:3–18`, `benchmark.py:204–205`). A later cache or `runs` symlink would violate the exclusive-output claim. `test ! -e .venv` also does not reject a dangling symlink. Setup deliberately runs outside Bubblewrap, so it needs its own path discipline.

**Prerequisite:** require canonical descendants of the exclusive root, reject links in all relevant ancestors and writable destinations, and execute a read-only, closed source snapshot containing only manifested imports. Verify again at dispatch or copy the verified inputs into that immutable run snapshot. Preserve the manifest instead of treating an editable file list as self-authenticating.

## Required execution prerequisites, not findings of an existing compromise

- **Resolve and bind the runtime before calling a run reproducible.** `requirements.in` pins NumPy 2.3.5 and CuPy CUDA12 14.2.0; transitive CUDA dependencies will only be fixed by the future `uv pip compile --generate-hashes`. `SETUP.sh:15–19` uses wheel-only resolution and explicit venv sync with `--require-hashes`, which is a sensible route. Today neither `.venv` nor `requirements.lock` exists. The controller only checks their existence and records the lock's hash (`benchmark.py:198–209`); it does not verify that the installed distribution inventory matches that lock or capture uv, Bubblewrap, driver, NVRTC, GPU/device identity and NumPy/CuPy versions. Record the resolved wheel hashes, installed inventory and toolchain/device identities, and confirm the exact environment is the one mounted at `/env`. A lock hash alone cannot attest installed bytes.
- **Constrain setup configuration as well as installation paths.** Setup explicitly uses the system Python as the interpreter, creates a new venv, disables managed-Python downloads, and redirects uv/pip caches into the lane. It contains no apt, sudo, driver update, service change or system-package write. Those are positive properties. It still inherits host uv configuration/environment and is not a filesystem sandbox. Use an explicit index/config policy and record it; keep any failed partial environment/lock as an identified failed attempt rather than silently overwriting it. No global Bubblewrap configuration change is needed or authorized.
- **Make the scheduling contract literal.** Capacity is checked before setup and each worker (`SETUP.sh:4–6`, `benchmark.py:115–120`), not continuously during setup or a worker. The worker loop never calls `assert_capacity()`. The current documentation's “stop on active price-run detection” therefore means boundary checks, potentially one full worker apart. One controller is sequential, but there is no lock against a second benchmark controller. Require an exclusive orchestration lease/lock and either monitor the active-run guard during work or document that the parent must hold exclusive release until the benchmark terminates.
- **Do not treat GPU compatibility as established by installation syntax.** Official CuPy 14.2 documentation supports Python 3.14, the NumPy 2.3 family, CUDA12 wheels and the `[ctk]` wheel approach; NVIDIA lists RTX3070 at compute capability8.6. These sources reveal no advertised compatibility contradiction in the selected route. Actual wheel availability/resolution, driver/library visibility inside this namespace, NVRTC compilation and telemetry remain unqualified. Qualify them only after release, under the same isolation and bounds; do not fall back to global driver/toolkit changes. [CuPy installation](https://docs.cupy.dev/en/stable/install.html), [NVIDIA compute capabilities](https://developer.nvidia.com/cuda/gpus).

The named 24,880,496-byte historical public archive matches SHA-256 `05b3d80d080aa51ec48fed387caecd0197ca64efe141eb18dfa33af5830a5950`. All twelve mapped source/fixture/expected-output archive members match the package byte-for-byte after the documented gzip decoding. No package symlinks were present. This verifies origin and copying, not correctness of the historical predictions.

**Worker isolation:** the planned command uses new mount/PID/user/network namespaces, drops capabilities, clears the environment, mounts `/usr` and the venv/code/input read-only, mounts one view only, and writes to a fresh `/out`. Expected answers and the live project checkout are not mounted. `/proc` is a namespace procfs, not a host-proc bind. GPU device nodes are only added for GPU workers. No worker source read in this review opens the active checkout, seeds or truth.

**Order before GPU use:** reference profiling precedes the hotspot gate and all adapter selection (`benchmark.py:211–228`). Worker namespace checks run before adapter import (`capsule/worker.py:30–40`); CuPy is imported and context/JIT initialized only in the GPU branch (`capsule/adapter.py:39–49`). The unchanged observer is imported earlier, but its inspected top-level imports are standard-library-only and do not execute the experiment. This conclusion covers the intended controller path, not arbitrary direct invocation of internal modules or unverified venv startup hooks.

**CPU budget:** `sched_setaffinity` limits the controller and inherited workers to two allowed logical CPUs (`benchmark.py:200–203`). This does not reserve physical cores or prohibit all other host work; the parent-release assertion correctly acknowledges that distinction. OpenBLAS and OpenMP are capped at one thread in the child environment (`:101–102`). There is no overall thread-count quota, but the advertised limit is two assigned vCPUs, not two operating-system threads. Setup's documented command also uses a two-CPU affinity.

## Timing, outcomes and status accuracy

The benchmark keeps profiling separate from timed observations. Three full observations per fresh worker include one initial and two warm invocations; array/GPU packing stays inside whole-observer timing. GPU context and explicit JIT compile occur before those observations and are separately recorded. GPU event time is synchronized, transfers are explicitly timed, and the parent includes process overhead in its cold estimate. Controls and measurement use distinct compiler-cache directories. These are appropriate development-screen choices.

The “cold process upper” at `benchmark.py:237` subtracts the two warm observer durations from the whole three-iteration process. It still includes all three serializations, monitoring/polling and other between-iteration overhead; it is not a directly measured one-observation cold run. Keep its upper-estimate label. Adapter metrics are cumulative across observations, not per-iteration (`capsule/adapter.py:5–8`; `capsule/worker.py:72–75`). Fixed backend order and two warm observations do not support robust performance or p95 claims; the package already disclaims those. Before integrating an alleged gain, measure independent cold one-observation workers and repeat the bounded performance comparison under controlled load. No numerical-equivalence formula or attack logic was reassessed here.

`STATUS.json` is accurate in reporting **BLOCKED**, unexecuted/uncompiled code, and the 18 verified files. “Preparation complete” can mean authored files exist; it cannot mean that only permission is missing. Add the review prerequisites to the blocked reason. `current_checkout_modified:false` should be read as “this lane made no checkout edits,” not as a claim that the live checkout is clean; [REPORT.md:21](REPORT.md) explicitly records the engineer's uncommitted work.

There is also a small provenance-label mismatch: `STATUS.json:24` records the raw manifest-file SHA-256, while `benchmark.py:207` will record a canonical-JSON digest under the same field name. Both can be valid identities, but name the representation or record both to prevent an apparent freeze mismatch later.
